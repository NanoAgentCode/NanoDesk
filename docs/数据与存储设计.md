# 数据与存储设计

## 1. 数据目录

主要运行时文件位于 Tauri app data 目录。后端启动时创建 app data、`logs/` 和 `temp/`，并打开六个 SQLite 文件；`settings.json` 在保存设置时写入，`skills/` 在首次列举本地 Skills 时创建：

```text
nanodesk-config.sqlite3
nanodesk-conversations.sqlite3
nanodesk-knowledge.sqlite3
nanodesk-project-index.sqlite3
nanodesk-runtime.sqlite3
nanodesk-observability.sqlite3
settings.json
logs/
skills/
temp/
```

所有 SQLite 连接启用 WAL，以提升桌面场景下的写入可靠性和读写体验。

Windows 默认 app data 路径为 `%APPDATA%\com.nanodesk.desktop`；`nano --data-dir <目录>` 只覆盖该次 CLI 使用的数据目录。

并非所有状态都在上述文件中：项目入口、当前项目、主题、侧栏折叠、Skills 启用状态和来源、Node/Python 路径、关闭行为等 UI 偏好保存在 WebView `localStorage`；Windows 开机自启动由当前用户注册表 `Software\Microsoft\Windows\CurrentVersion\Run` 下的 `NanoDesk` 值控制。

## 2. 领域业务库

业务数据按用途拆分为四个文件：

| 文件 | 数据范围 |
| --- | --- |
| `nanodesk-config.sqlite3` | `model_suppliers`、`model_configs`、`mcp_servers`、`ops_servers` |
| `nanodesk-conversations.sqlite3` | `conversations`、`messages`、`rag_*`、`profile_*`、`user_profile_*` |
| `nanodesk-knowledge.sqlite3` | `items`、`memories`、`memory_*` 及动态 `memory_vectors_<维度>` |
| `nanodesk-project-index.sqlite3` | `code_*`、`project_index_*` |

`src-tauri/src/db.rs` 负责公共 schema，`db/storage.rs` 负责文件定位和领域表裁剪，各领域 store 使用对应连接。会话、消息、RAG 与画像继续位于同一文件，因此原有原子事务不变。会话库内保留只由程序同步的 `model_configs` 引用镜像，用于维持模型删除时 `ON DELETE SET NULL` 的外键语义；权威配置只存在于配置库。

### 2.1 items

用于本地笔记、提示词等工作区条目。

核心字段：

- `id`
- `kind`
- `title`
- `body`
- `status`
- `tags_json`
- `created_at`
- `updated_at`

配套 `items_fts` 支持 title、body、tags 全文检索。

### 2.2 model_configs

保存从供应商模型列表中选用的聊天、embedding 和 ASR 模型配置。供应商连接由前端“供应商管理”维护，并持久化到配置库的 `model_suppliers` 表（`id`、`name`、`provider`、`base_url`、`api_key`、创建及更新时间）；选中的具体模型及其用途、路由属性持久化到 `model_configs`。

核心字段：

- `provider`
- `base_url`
- `model`
- `api_key`
- `context_window`
- `model_kind`
- `routing_group`
- `routing_enabled`
- `routing_cost`
- `routing_quality`
- `routing_speed`
- `routing_tasks_json`
- `embedding_provider`
- `embedding_base_url`
- `embedding_model`
- `embedding_api_key`

聊天模型可以保存多组。前端模型路由分配固定列表、四种智能策略、兜底、嵌入和 ASR 用途；四种策略各保存一个模型 ID。旧多选数组先取第一个字符串 ID，再校验聊天用途；无效时清空，不继续找后面的有效 ID。全局 Embedding 保存为 `embedding-config`。同一记录内未填写 embedding URL 或密钥时，底层函数使用其 `base_url` 或 `api_key`；只有会话 RAG 缺少全局配置时改用当前聊天记录，手工记忆与项目索引走无向量降级。LLM、Embedding 和模型发现仅在地址字符串含 `localhost` 时允许空密钥，`127.0.0.1` 不适用。选中的 LLM/Embedding 保存连接值，修改供应商不会自动更新这些记录，需重新选择。

### 2.3 conversations 与 messages

`conversations` 保存会话：

- `model_config_id`：会话绑定模型，可为空。
- `project_path`：项目会话的真实项目路径；普通会话为空。
- `archived`、`archived_at`：归档状态。

`messages` 保存消息：

- `conversation_id`
- `role`
- `content`
- `metadata_json`
- `created_at`

消息正文保留原始 Markdown 文本；GFM、项目路径链接和 KaTeX 公式都在前端渲染阶段解释，不生成额外持久化表或派生 HTML。

删除会话会级联删除消息、RAG 文件和 chunk。归档不会移动消息或附件，只改变会话状态；归档预览通过会话的 `project_path` 或 app data `temp/` 定位历史图片附件。

### 2.4 图片附件

图片附件不单独建表，路径保存在消息正文中。前端会生成如下块：

```text
图片附件：
- image.png: .nanodesk/uploads/images/...
需要识别图片文字时，请调用 ocr_image 工具。
```

实际文件存放在附件根目录下的 `.nanodesk/uploads/images/`：

- 项目会话：附件根目录为 `conversation.project_path`。
- 普通会话：附件根目录为 app data 下的 `temp/`。

`read_chat_image_attachment` 只允许读取 `.nanodesk/uploads/images/` 下的受支持图片，返回 data URL 给前端缩略图和大图预览。

### 2.5 RAG 表

RAG 使用四类结构：

- `rag_files`：文件元数据、hash、chunk 数、状态。
- `rag_chunks`：文本分块。
- `rag_embeddings`：chunk embedding 二进制向量、维度、模型名。
- `rag_chunks_fts`：随 chunk 同步维护的全文索引；当前召回命令尚未使用该索引。

RAG 数据按 `conversation_id` 隔离。当前实现是对话级轻量 RAG，不是全局知识库；索引和查询都依赖 Embedding 服务，召回按余弦相似度排序，目前没有 FTS 降级路径。

归一化文本最多 200 万字符，但分块最多 120 个，每块目标 1600 字符、重叠 180 字符，达到分块上限后尾部不再索引。原始导入文件另受 10 MiB 上限约束；允许导入不等于全文已进入检索。

### 2.6 memories

长期记忆以主业务 SQLite 作为一致性边界，由关系数据、嵌入式向量索引和知识图谱共同组成：

- `memories`：记忆正文及生命周期状态。
- `memories_fts`：标题、正文和标签的 FTS5 全文索引。
- `memory_embeddings`：记忆与向量 rowid、模型、维度、内容 hash 的映射。
- `memory_vectors_<维度>`：sqlite-vec `vec0` 虚拟表；不同向量维度独立建表，向量只保存在本机。
- `memory_entities`、`memory_entity_links`：从标题、标签、正文 hashtag 和反引号概念生成的实体及记忆证据链接。
- `memory_relations`：同一条记忆中实体的共现边，保留 `evidence_memory_id` 以便更新和删除时精确回收。
- `memory_entities_fts`：图谱实体入口的全文索引。

`memories` 核心字段：

- `title`
- `content`
- `tags_json`
- `enabled`

发送对话时只注入启用记忆。当前词法支路加载启用记忆后在内存做词项评分，与可选 sqlite-vec KNN 和图谱实体 FTS/一跳扩展通过 RRF 融合，并优先保留最多 3 条 `personalization:always` 记忆。`memories_fts` 用于管理搜索，没有参与当前聊天的词法支路。Embedding 缺失或请求失败时保留词项评分和图谱召回，不阻断记忆保存或对话。

创建或更新记忆时会同步全文索引和图谱，并在记忆启用且 Embedding 服务可用时更新向量；删除时同步回收向量及无引用实体。当前不会把旧单库中的向量或记忆复制到知识库。已有知识库中的缺失图谱在数据库打开阶段自动补建，缺失或过期向量在召回时按批次生成。记忆向量复用全局“嵌入模型”配置：启用记忆的标题、标签、正文以及检索问题会发送给该服务，生成的向量只写入本地知识库。

历史 `personalization:*` 标签仍作为普通记忆标签保留，继续支持编辑、启用和删除，但不再参与用户画像聚合。新的自动画像不会写入 `memories`。

### 2.7 用户画像表

用户画像与普通记忆独立存储。`profile_settings` 保存开关、模型目的地、批量阈值和滚动预算；`profile_state` 保存 generation、单调 revision 和本地过滤统计。

- `profile_observations`：只保存源用户消息引用、字符统计、候选 hash、分类和预处理租约，不复制候选正文；`skipped` 观察作为本地待确认项保留，展示时关联读取原消息，加入画像或丢弃均不改写原聊天消息。
- `profile_extraction_batches`、`profile_batch_observations`：固定批次成员、模型目的地快照、状态、重试和 Worker 租约。
- `profile_usage_attempts`：记录候选字符、估算输入 Token，以及 provider 返回时的实际输入/输出 Token。
- `user_profile_facts`、`user_profile_fact_sources`：确定性 Reducer 写入的画像事实及来源关系；删除聊天消息后事实保留，来源关系中的消息和观察引用置空。
- `profile_fact_tombstones`、`profile_batch_commits`：阻止删除后的旧任务复活事实，并保证批次最多提交一次。
- `profile_foreground_leases`：桌面端与 CLI 的前台聊天启动门，防止画像模型在聊天进行时新启动。

用户消息与观察引用由 `db/conversation_store.rs` 在同一个 SQLite 事务中写入；观察的 `raw_character_count` 当前记录 UTF-8 字节数，预处理后的候选字符数按 Unicode 字符统计。画像状态机与 Reducer 位于 `db/profile_store.rs`。清洗、组批和模型调用均在后台进行；自动路径发送本地筛出的候选片段和批内序号，人工“加入画像”路径发送所选用户输入的前 12000 个字符。两条路径均不额外发送当前画像、会话 ID 或消息 ID，但当前清洗器不保证清除候选文本自身包含的图片引用、路径或结构化内容。关闭画像会递增 generation 并清理未处理来源，现有事实保留但停止注入；清空画像会另行删除事实和画像来源，不影响普通记忆或聊天历史。

### 2.8 项目索引表

项目索引按 `project_path` 隔离，是项目级能力，不绑定某个会话。当前包含代码索引表和通用项目文档索引表。

通用项目文档索引使用四类结构：

- `project_index_runs`：按 `project_path + indexer` 记录每次项目索引构建的状态和统计。
- `project_index_chunks`：普通文档、配置和数据文件的文本片段。
- `project_index_chunks_fts`：维护项目文档片段全文索引，但当前召回未使用它。
- `project_index_embeddings`：可选向量；依赖全局 embedding 配置，失败时保留文本、标题和路径 LIKE 匹配。

文档索引器的 `indexer` 当前为 `document`。后续可以继续加入 PDF/Office、日志、图片 OCR 或自定义索引器，但需要继续遵守项目路径隔离和文件边界校验。

### 2.9 代码索引表

项目代码索引使用六类结构：

- `code_index_runs`：每次项目代码索引构建的状态和统计。
- `code_entities`：函数、组件、类型、接口、Rust struct/enum、Tauri command 等代码实体。
- `code_relations`：import/use、函数调用和前端 `invoke(...)` 桥接关系。
- `code_chunks`：按文件和行号切分的代码文本片段。
- `code_chunks_fts`：维护代码片段全文索引，但当前召回未使用它。
- `code_embeddings`：可选的代码片段向量索引；依赖全局 embedding 配置，失败时不影响实体和文本检索。

发送代码类问题时，前端调用 `load_base_context`，后端通过 `project_retrieval.rs` 调用数据库的 `search_code_index` 召回相关实体和片段，再由前端注入 system message；独立的 `search_code_index` command 仍保留。

### 2.10 mcp_servers

保存 MCP server 配置：

- `transport`：`stdio`、`sse`、`streamable_http`
- `command`、`args_json`、`env_json`、`working_dir`
- `url`、`headers_json`
- `enabled`

运行中的 MCP session 不落配置库，只存在 `McpClientManager` 内存状态中。

### 2.11 ops_servers

保存 Ops SSH 服务器配置：

- `name`
- `host`
- `port`
- `username`
- `auth_method`
- `key_path`
- `password`
- `remote_dir`

当前 UI 支持 SSH Agent、密钥路径和密码认证相关配置。交互式 SSH session 只保存在运行时内存中，关闭或断开后不持久化。

## 3. 运行时库

运行时库文件：`nanodesk-runtime.sqlite3`。

### 3.1 agent_runs

记录一次用户消息触发的 Agent 流程：

- `conversation_id`
- `project_path`
- `model_config_id`
- `trigger_message_id`
- `status`
- `error`
- `created_at`、`updated_at`、`completed_at`
- `plan_json`、`plan_updated_at`：最近一次结构化任务计划及更新时间。

### 3.2 agent_steps

记录流程阶段，例如用户消息、模型调用、工具执行、续写、错误：

- `run_id`
- `kind`
- `status`
- `input_summary`
- `output_summary`
- `metadata_json`

### 3.3 agent_tool_calls

记录模型请求执行的工具：

- `run_id`
- `message_id`
- `name`
- `args_json`
- `status`
- `attempt_count`：已经实际开始执行的次数，从 `approved` 原子切换到 `running` 时递增。
- `max_attempts`：允许的最大执行次数，默认 3。
- `result_summary`
- `error`

工具调用状态服务于 UI 展示、用户审批、执行结果回放和故障排查。

## 4. 观测库

观测库文件：`nanodesk-observability.sqlite3`。

`observability_spans` 字段：

- `id`
- `trace_id`
- `parent_span_id`
- `operation`
- `category`
- `entity_type`
- `entity_id`
- `status`
- `started_at`
- `ended_at`
- `duration_ms`
- `input_summary`
- `output_summary`
- `error`
- `metadata_json`

索引：

- `trace_id, started_at`
- `operation, started_at`
- `status, started_at`

设计原则：

- 观测数据独立于主业务数据。
- sink 失败不阻断业务。
- 默认查询限制为 200，后端 clamp 到 1 到 1000。

## 5. 系统日志

桌面端启动时在 app data 的 `logs/` 下初始化 `DailyFileLogSink`：

- 文件名为 `YYYY-MM-DD.log`，采用追加写入。
- 每条记录包含时间、级别、target、消息和结构化字段。
- 启动及后续写入时会清理超过保留期的日期日志；当前保留最近 7 天。
- 日志写入失败会回退到标准错误输出，不应阻断主业务。

系统日志和 `observability_spans` 用途不同：前者适合启动、操作边界和 sink 故障排查，后者用于应用内按 trace 查看调用链。

### 5.1 凭据存储边界

当前实现没有应用层静态加密：供应商、聊天/embedding 模型 API key、MCP 的环境变量与 headers、Ops 密码保存在 `nanodesk-config.sqlite3`。`settings.json` 保存 Tavily API key 和 ASR 配置；绑定供应商的 ASR 配置只保存供应商 ID、模型及语言，服务地址和 API key 从 `model_suppliers` 读取，未绑定供应商的旧 ASR 配置仍可保存地址和 API key。它们依赖操作系统用户目录权限保护；复制 app data、数据库或备份时应按敏感凭据处理，日志和观测摘要不得记录这些原值。

## 6. 文件边界

项目文件 API 以 `project_path` 作为根目录。所有相对路径必须归一化后解析，避免 `..` 或绝对路径越界。删除文件要求传入确认文本，降低误删风险。

`list_project_files` 返回的是轻量项目文件列表，前端会在打开或切换项目时把它缓存在内存中，用于侧栏/上下文展示和 Markdown 消息里的项目文件链接解析。该缓存不写入 SQLite，不读取文件正文，也不等同于 RAG 或语义索引。

Markdown 渲染层会基于这份文件列表解析以下内容：

- 项目相对路径：`src/App.tsx`
- 带行号或列号的路径：`src/App.tsx:12`、`src/App.tsx:12:3`
- 裸文件名：`MarkdownMessage.tsx`
- 已有 Markdown 文件链接：`[MarkdownMessage.tsx](MarkdownMessage.tsx)`

裸文件名只在当前项目文件列表中解析，若存在同名文件，前端优先选择目录更浅、路径更短的条目。真正打开文件所在位置时仍调用后端 `open_project_file_location`，由后端按 `project_path` 重新解析和校验。

`read_absolute_file` 用于 RAG 文档导入，可读取普通文件、PDF、doc、docx、pptx、xlsx 等格式，最大 10MB。项目内普通文本读取限制更低，避免把大型文件直接塞进对话上下文。

图片附件和 OCR 都基于显式根目录解析；预览需传正确的项目或 `temp/` 路径。当前 Agent 策略拒绝 `.nanodesk`，因此保存在 `.nanodesk/uploads/images/` 的附件不能直接 OCR；允许的普通项目图片路径才可进入执行链路。文件/OCR 工具检查路径，命令工具只设置工作目录并检查字符串规则，不提供文件系统沙箱。上传的 RAG 文档提取另使用操作系统临时目录下的 `nanodesk-rag-extraction/`，提取结束后尝试删除临时文件。

## 7. 迁移策略

当前四个领域业务库采用 `CREATE TABLE IF NOT EXISTS` 加 `ensure_column` 的轻量 schema 演进方式。

这套方式只演进当前领域库：`Database::open` 从传入的基础文件名派生四个领域文件，不打开或导入旧 `nanodesk.sqlite3`。旧单库文件保持原样，但其中的配置、对话、记忆和向量不会自动出现在新库；`old_base_database_is_ignored` 测试明确覆盖此行为。不能将分库升级描述为自动数据迁移。

适用场景：

- 小型桌面应用。
- 新增可空字段或带默认值字段。
- 低频 schema 演化。

不适合场景：

- 字段类型重构。
- 大规模数据迁移。
- 复杂索引重建。

后续如果 schema 演化频繁，应引入版本表和显式 migration。
