# NanoDesk 用户画像异步批处理设计

## 1. 文档状态

- 状态：首版核心链路已实现；自动测试覆盖见第 19 节，完整设计要求及延迟验收尚未全部完成
- 范围：设计与首版实现基线
- 目标版本：用户画像替代现有自动个性化记忆
- 已确认决策：
  - 普通手工记忆继续保留，可创建、编辑、删除。
  - 用户画像独立存储，不可编辑，可单条删除或全部清空。
  - 仅从用户输入提取画像，不分析助手回复。
  - 不迁移现有个性化记忆；新系统从启用后的新消息开始积累。
  - 桌面端与 `nano` CLI 使用同一套画像数据和批处理逻辑。
  - 画像生成不按每条消息调用模型，而是累积后批量处理。
  - 超长输入不进入普通批次，单独调用模型一次。
  - 自动路径发送本地筛选出的画像候选片段；人工“加入画像”路径发送所选输入的前 12000 个字符；两者均不发送当前已有画像。
  - 模型输出候选断言与撤回操作，最终合并由本地确定性规则完成。
  - 后台先用本地宽松规则筛出画像候选片段；减少普通问答误入是设计目标，当前词法规则不能完全保证。
  - 画像调用受滚动 60 分钟和滚动 24 小时次数、候选字符预算约束。

## 2. 背景与问题

改造前的个性化能力建立在 `memories` 表之上：前端使用正则从单条用户输入识别偏好或身份信息，再调用 `upsert_personalization_memory` 写入带特殊标签的普通记忆；`get_user_profile` 又从这些记忆动态聚合画像。该实现有以下边界：

1. 单条消息和正则规则难以理解隐含表达、补充关系与否定关系。
2. 自动画像与手工记忆共享数据模型，编辑、禁用、召回和来源语义相互耦合。
3. 如果逐条调用模型进行语义提取，会增加调用次数、费用和资源竞争。
4. 大段错误日志、代码或 JSON 容易造成误提取并浪费模型输入。
5. 桌面端已有自动个性化入口，CLI 当时尚没有等价的画像生成路径。

本设计将“手工记忆”和“用户画像”拆成两个独立领域。手工记忆继续使用现有混合召回；用户画像改为持久化观察池、异步批处理和本地确定性合并。

## 3. 目标与非目标

### 3.1 目标

- 画像语义提取不进入正常聊天的响应关键路径；不承诺消除共享网络、云端额度或本地模型资源造成的所有间接竞争。
- 多条用户输入合并为一次模型调用，减少费用和重复更新。
- 只把可能形成稳定画像的候选片段发送给模型，避免重复处理全部用户输入。
- 画像事实结构化、可追溯、可删除，并能处理明确的新增、替换和撤回。
- 纯日志、代码和其他粘贴内容不进入普通画像批次。
- 队列跨重启保留，桌面端和 CLI 不会重复消费同一任务。
- 云端数据流向对用户明确可见；自动路径只发送必要的过滤文本，人工确认路径仅在用户点击“加入画像”后发送所选输入。

### 3.2 非目标

- 不把普通手工记忆迁移为画像。
- 不把现有带 `personalization:*` 标签的历史记忆转换为画像。
- 不分析助手回复、附件正文或完整聊天历史。
- 不为画像建立向量索引或知识图谱。
- 不在 NanoDesk 退出后安装或运行系统常驻服务。
- 首版不允许直接编辑画像事实；纠正通过后续自然语言表达完成。

## 4. 总体架构

```text
用户输入
  -> profile_observations 持久化观察引用
  -> 后台预处理：清洗、候选过滤、分类与去重
  -> 混合阈值调度器
       |- 普通批次
       `- 超长输入独立批次
  -> 后台一次模型调用
   -> JSON 反序列化与逐项过滤
  -> 本地 Profile Reducer
  -> user_profile_facts 原子更新
  -> 下一轮桌面端或 CLI 对话注入画像
```

字符、消息数和时间阈值只统计通过本地候选过滤的片段。当前过滤器依赖第一人称或显式指令与稳定属性关键词的组合，不能完全排除含这些词的提问、一次性任务、第三方转述或结构化文本；更完整的排除规则仍是设计目标。

画像处理与聊天共享模型配置，但不复用聊天请求。用户消息与观察引用在同一个本地数据库事务中保存，正常聊天不执行清洗、不创建批次、不等待画像生成结果。画像从后续对话开始生效，不保证当前消息形成的画像能用于当前回复。

## 5. 输入收集与清洗

### 5.1 收集范围

收集满足以下条件的输入：

- 角色为 `user`。
- 属于持久化会话，且已经成功写入 `messages` 表。
- 画像功能已开启。
- 不是附件正文、工具结果或应用自动生成消息。

临时 CLI 会话默认不收集画像，因为其消息不进入持久化对话历史。项目会话和可恢复 CLI 会话正常收集。

观察收集不复制消息正文，在保存 `messages` 的同一事务内分配单调 revision 并执行 `INSERT OR IGNORE`，写入消息 ID、会话 ID、原文 UTF-8 字节数和时间。`raw_character_count` 当前使用 `String::len()`，不是 Unicode 字符数；候选字符数在后台按 `chars().count()` 统计。聊天热路径不执行画像清洗，也不增加第二次数据库锁竞争。

### 5.2 本地清洗

本地预处理 worker 在组建模型批次之前执行清洗和宽松候选过滤，但不负责生成最终画像事实。当前已实现：

- 识别并排除 fenced code block。
- 按固定关键词排除部分 stack trace、错误行、源文件行号和敏感凭据行。
- 保留代码块前后由用户书写的自然语言说明。
- 按句末标点拆分片段、裁剪边缘标记，限制每段最多 500 字符，候选总长最多 12000 字符。
- 没有匹配画像句式的输入标记为 `skipped`，不调用模型。

以下仍是规划要求：移除 Markdown 图片与附件引用，完整识别编译输出、未围栏代码、JSON、XML、SQL 和终端输出，折叠候选内部的重复空白，以及可靠排除第三方、引用、假设和临时任务。当前 `input_kind` 分类不等于已过滤对应正文。

清洗器以第一人称或显式指令及稳定属性关键词决定是否保留片段。设计上希望覆盖以下长期用户属性；当前词法规则的覆盖不完整：

- 明确的个人身份、角色、环境或长期项目陈述。
- 回答语言、长度、格式、语气等稳定偏好。
- 常用技术、工作方式、兴趣和持续性习惯。
- 对上述事实的明确否定、停止、替换或纠正。
- “记住我……”等明确要求写入画像的自述。

以下是应排除的内容范围，其中普通手工记忆和应用自动消息通过调用方元数据排除，其余尚不能由当前词法过滤器完整保证：

- 单纯提问、一次性任务要求或临时操作步骤。
- 没有第一人称归属的技术名词和产品名称。
- 第三方人物信息、示例、假设、引用和转述。
- 已被识别为代码、日志、附件或结构化数据的正文。
- “记住这段错误/知识/任务”等应进入普通手工记忆的内容。

候选过滤允许使用小型、可测试的词法和句式规则，但规则只决定“是否值得交给模型”，不直接决定画像维度和值。自动路径无法确定时不发送整条消息，而是将该输入保留在本机待确认区；只有用户明确点击“加入画像”后，所选输入才作为人工候选发送。

预处理只保存分类、候选字符数、候选内容 hash、候选类型和清洗器版本，不保存清洗后的正文。模型 worker 在调用前和重试时使用当前代码重新从源消息构建候选片段，并校验 hash 一致；目前不会依据保存的 `cleaner_version` 选择旧版清洗器。源消息已删除时，该观察自动失效。

同一个固定批次内，候选 hash 完全相同的重复输入只发送最新来源的文本，其他已选来源仍可作为审计证据关联。当前去重范围是批次，超出 12 条成员上限而留在 ready 池的重复观察仍可能在后续批次再次发送；没有覆盖整个 pending 窗口的去重账本。

## 6. 批处理触发规则

### 6.1 普通批次

默认使用混合触发，任一条件满足即可生成批次：

| 指标 | 默认值 | 目的 |
|---|---:|---|
| 累计候选字符数 | 3000 | 只统计可能形成画像的过滤片段 |
| 候选观察数 | 12 | 防止大量短候选长期积累 |
| 空闲时间 | 30 分钟且至少 500 个候选字符 | 避免少量普通信息形成高频小请求 |
| 最长等待 | 24 小时 | 让不足 500 字符但确有价值的短画像最终得到处理 |
| 显式画像指令 | 聊天完成后尽快处理 | 尊重“记住我……”的明确意图 |

设置页允许调整候选字符阈值、空闲时间和最长等待时间。候选观察数作为内部安全上限，不增加额外设置项。显式画像指令可以绕过批量字符和时间门槛，但不能绕过模型目的地确认、前台启动门和调用预算。

用户也可以在画像卡片点击“立即生成”。该操作先预处理最多 16 条观察，至多新建一个 `trigger_kind = 'manual'` 批次，再按统一领取优先级处理一个可执行批次并等待模型提取；不保证一次清空观察池或处理刚建的批次。它绕过普通批次的字符、数量和时间门槛，但仍遵守模型目的地、前台启动门和调用预算。没有有效候选或任务被延后时，界面通过按钮 Tips 返回状态；当前 `generated` 表示模型结果已解析并尝试提交，不保证产生新事实或提交未被 generation/epoch 屏障拒绝。

普通批次最多包含 12000 个去重后的候选字符和 12 条观察。普通触发按 observation revision 从旧到新选择成员，显式或人工触发优先选择对应候选；剩余观察等待后续 worker 周期再次组批，每个周期最多新建一个批次，每个批次每次尝试只进行一次模型请求。

### 6.2 调用预算

云端和本地模型统一受调度预算控制，默认值为：

| 预算 | 默认值 |
|---|---:|
| 最近 60 分钟画像请求尝试 | 2 次 |
| 最近 24 小时画像请求尝试 | 8 次 |
| 最近 24 小时候选输入字符 | 30000 字符 |

领取批次时先预占一次尝试和批次创建时冻结的去重候选字符数，失败重试同样预占。当前预占发生在候选请求重建和实际调用之前，因此空来源取消或请求重建失败也可能计数；删除部分来源后也不会重算已冻结字符数。预算使用 UTC 时间戳上的滚动窗口，不依赖本地日期切换或系统时区。达到预算后任务保持待处理并顺延到最早可用时间，不丢弃观察。设置页显示最近 24 小时预占次数、候选字符数和估算 Token；如果 provider 返回实际 usage，则同时记录实际输入、输出 Token。

预算的目的不是准确计费，而是提供稳定上限。默认值允许用户调整，但界面必须明确提高预算会增加云端费用或本地资源消耗。

### 6.3 超长输入

后台预处理 worker 按以下固定顺序分类：

1. 候选清洗在原文超过 131072 字符时只处理首尾各 65536 字符；原文字符统计和结构化占比仍遍历完整输入，因此当前不能保证总 CPU 开销有固定上限。
2. 清洗并执行画像候选过滤；没有候选片段时标记为 `skipped`。
3. 满足任一超长条件，进入 `long` 独立批次。
4. 其余输入进入 `normal` 普通批次。

观察必须先从 `pending_preprocess` 转为 `ready_normal`、`ready_long` 或 `skipped`，调度器只能选择 ready 状态观察组批。因此长输入分类不会发生在普通批次固定成员之后。

满足任一条件即视为超长输入：

- 单条原文超过配置的超长阈值，默认 8000 字符。
- 代码、日志或结构化内容占原文的 60% 以上。
- 截断后的单条候选文本达到 12000 字符。

超长输入不加入普通批次，可以在前台聊天期间先创建独立待处理批次，但只有前台租约释放后才能领取并启动模型。当前沿用同一词法清洗器并直接截断到最多 12000 个候选字符，没有独立的“无法可靠缩减”判定；没有候选时才标记为 `skipped`。这里的“调用一次”表示每个尝试不拆分为多个画像请求；网络失败仍按统一重试策略重新尝试。

### 6.4 前台优先级

- 收集观察与用户消息共用一次本地 SQLite 事务。
- 正常聊天请求进行中时，调度器可以创建待处理批次，但不得开始画像模型调用。
- 已经开始的画像请求首版不强制取消；它不在聊天因果关键路径上，但仍可能与随后到来的聊天共享网络或本地模型资源。
- 后续若运行指标表明存在资源竞争，再增加可取消请求或模型并发优先级，不在首版预建复杂调度框架。

桌面端和 CLI 使用数据库中的短租约记录前台聊天活动。模型请求开始前写入租期 30 秒的前台租约，回复期间每 10 秒续租；桌面流式请求在成功、模型错误或取消后释放。非流式桌面请求和 CLI 在请求结束后释放，但续租自身报错可能提前返回并依赖租约过期恢复，并非所有异常都由 `finally` 释放。该租约不覆盖保存用户消息和准备检索上下文的整个前端发送流程。

画像 worker 通过统一的批次领取事务执行“模型启动门”：清理过期前台租约、确认当前没有有效前台租约、核查模型目的地及预算，直接把可领取批次改为 `model_started`，递增 epoch 和尝试次数并写入预算记录。当前没有独立的 `leased` 阶段。事务成功后重建请求并调用模型；新聊天获取前台租约不等待已经开始的画像请求。

该协议可以阻止另一进程在已知聊天期间启动新画像请求，但不能取消已经发出的请求，因此本设计保证“无同步等待和无因果阻塞”，不宣称在所有共享资源条件下延迟绝对不变。

## 7. 模型选择与调用协议

### 7.1 模型选择

画像设置保存一个 `model_config_id`，指向现有模型配置，不新建一套 provider、URL 或 API key。前端只列出聊天模型；首次配置默认选择当前聊天模型或列表中的第一个聊天模型，CLI 读取同一配置。后端当前只拒绝 `embedding-config` 和仅 embedding 配置，未单独拒绝 ASR 配置。设置页展示配置名称和模型名；服务地址、provider 与低成本模型提示仍待补充。

批次在创建时冻结数据目的地快照：`model_config_id`、provider、规范化 base URL、模型名和这三项构成的目的地 hash；API key 仍只通过配置 ID 读取，不复制到批次，也不参与 hash。领取和重试领取时确认当前目的地与快照一致。模型被删除或目的地发生变化时，批次进入 `blocked_config_changed`；设置页“重试异常批次”会按当前已保存的画像模型更新异常批次快照并重置尝试次数，不自动改用新目的地。

### 7.2 请求内容

每个批次只发送：

- 通过本地候选过滤的用户自述片段，不发送同一消息中的其他自然语言。
- 用户在本地过滤待确认区点击“加入画像”时，发送该条被明确选择的用户输入，最长 12000 字符；点击“丢弃”不会发送。
- 片段在批次内的稳定序号；不发送消息 ID、会话 ID或时间戳。
- 固定画像维度、允许操作和 JSON 输出约束。

当前使用固定的简短提取提示词，没有独立提示词版本号或 provider JSON Schema 参数；通过提示词约束 JSON 结构，再用 Serde 反序列化和 Reducer 逐项过滤。不重复发送产品说明、示例对话或当前画像。严格 Schema 和提示词版本管理仍是规划要求。

不发送：

- 当前已有画像。
- 助手回复或推理内容。
- 完整聊天历史。
- 自动路径已经识别并过滤的 fenced 代码块和错误行；人工“加入画像”路径会发送所选原始输入，不能保证排除其中的附件引用、代码或日志。
- 普通手工记忆。
- 额外附加的本地消息 ID、会话 ID、时间戳或数据库 ID；候选文本本身包含的路径和其他标识符当前没有通用脱敏规则。

### 7.3 模型输出

模型只输出候选事件，不直接返回完整画像：

```json
{
  "operations": [
    {
      "action": "assert",
      "dimension": "tooling",
      "value": "Vue",
      "source_indexes": [2],
      "confidence": 0.94
    },
    {
      "action": "retract",
      "dimension": "tooling",
      "value": "React",
      "source_indexes": [2],
      "confidence": 0.91
    }
  ]
}
```

允许操作只有：

- `assert`：用户明确陈述当前稳定事实或偏好。
- `retract`：用户明确否定、停止或撤回某项事实或偏好。
- 没有值得形成长期画像的内容时返回空 `operations`；当前提示词只要求 `assert` 和 `retract`，Reducer 忽略其他 action。

模型不得根据日志中的技术名词、文件路径、第三方人物信息、假设性表达或助手内容推断画像。

## 8. 本地画像合并器

模型输出必须先经过本地校验，模型不能直接写数据库。

### 8.1 校验

- `dimension` 必须属于应用内置白名单。
- `value` 去除控制字符、折叠空白并截断为最多 500 字符；去除提示词样式标记仍是规划要求。
- `source_indexes` 仅保留当前批次中仍有效的引用，无有效来源的操作被忽略。
- 低于默认置信度阈值 0.75 的候选丢弃。
- 重复候选按标准化维度和值合并。
- 单个批次只遍历模型返回的前 20 个操作；越界维度、无效来源、低置信度或空值会被逐项忽略，不让整个批次失败。

当前反序列化忽略未知 JSON 字段，`operations` 缺失时默认为空；`confidence` 没有完整的 0 到 1 范围校验。非法 JSON 或字段类型不匹配会使批次失败，但严格拒绝未知字段、越界值及混合合法/非法操作的整个响应仍待实现。

### 8.2 维度基数

单值维度的新断言替换该维度旧值：

- `profile-name`
- `profile-role`
- `profile-environment`
- `response-language`
- `response-length`
- `response-format`
- `response-tone`

多值维度按标准化值去重并存：

- `tooling`
- `project`
- `workflow`
- `interest`

维度注册表由 Rust 后端维护，前端不自行决定合并规则。

后端分别维护维度类别、全局标志和单/多值规则，以及中文标签映射。当前标准化执行 trim、连续空白折叠和小写化，尚未执行 Unicode NFKC；首版不擅自把 `React` 与 `React.js` 等别名视为相同值。`category` 与 `global` 由 dimension 派生，模型不能指定。多来源事实的置信度取最近一次有效断言值，来源关系全部保留。

### 8.3 操作语义

- 单值 `assert`：相同值更新来源和时间；不同值原子替换旧事实。
- 多值 `assert`：相同标准化值去重，否则新增。
- `retract`：只删除同维度下可明确匹配的值；模糊撤回不扩大删除范围。
- 事实更新按来源的最大 observation revision 拒绝较旧断言；相同 revision 的冲突操作按模型返回顺序应用，不另按墙上时间排序。
- system message 要求当前用户消息高于已保存画像；首版将其定义为模型行为约束，而不是本地可证明的不变量。

所有事实变更、来源关系、删除屏障校验、租约 fencing 校验和批次提交账本在一个 SQLite 事务内提交。同一个 batch ID 最多提交一次；旧 worker 重新运行 Reducer 不等同于幂等，必须由持久化提交账本拒绝重复提交。

## 9. 数据模型

### 9.1 `profile_settings`

单行配置表：

- `enabled`
- `model_config_id`
- `character_threshold`
- `idle_seconds`
- `max_wait_seconds`
- `long_input_threshold`
- `rolling_hour_attempt_limit`
- `rolling_day_attempt_limit`
- `rolling_day_candidate_character_limit`
- `updated_at`

关闭画像功能时执行统一的隐私语义：停止收集和注入，递增 `profile_generation` 使所有旧任务失效；在同一事务中删除未处理观察与 batch-member 来源关系，把尚未完成的批次保留为不含消息 ID、模型目的地和正文的 `cancelled` 汇总记录。已有画像事实及其 processed 来源保留但不再使用；“清空画像”用于另行删除事实。重新开启后只处理新的用户消息，不恢复关闭前任务。

### 9.2 `profile_observations`

- `id`
- `source_message_id`
- `conversation_id`
- `raw_character_count`
- `candidate_character_count`
- `candidate_hash`
- `candidate_kind`：初始默认 `implicit`；当前自动预处理写入 `explicit` 或 `normal`，人工确认写入 `manual`
- `input_kind`：初始默认 `normal`；自动预处理写入 `plain`、`code`、`error_log` 或 `json`，人工确认写入 `manual`；长短由 `ready_normal`/`ready_long` 状态区分
- `cleaner_version`
- `status`：`pending_preprocess`、`preprocessing`、`ready_normal`、`ready_long`、`batched`、`processed`、`skipped`；关闭或清空时物理删除未处理观察
- `skip_reason`
- `profile_generation`
- `observation_revision`
- `preprocess_lease_owner`
- `preprocess_lease_expires_at`
- `preprocess_lease_epoch`
- `observed_at`
- `processed_at`

`source_message_id` 唯一，保证同一用户消息只收集一次。观察不保存第二份消息正文。预处理任务使用短租约，租约过期可被其他进程接管。预处理完成只能通过同时匹配 `status = 'preprocessing'`、owner、`preprocess_lease_epoch` 和当前 `profile_generation` 的条件更新提交；匹配失败的旧 worker 必须丢弃结果，不能把已取消观察恢复为 ready。删除源消息时级联删除观察；如果观察已经入批，提交阶段必须忽略所有来源已经删除的操作。

没有画像候选的 `skipped` 观察累加本地统计后保留为待确认项，仍只保存源消息引用而不复制正文。用户可将其改为高优先级 `manual` 候选并立即尝试生成画像，或删除观察记录；删除不会影响原聊天消息。形成画像来源的 processed 观察保留最小引用字段；未形成任何事实的 processed 观察可按 7 天保留期清理。

### 9.3 `profile_extraction_batches`

- `id`
- `trigger_kind`：`characters`、`count`、`idle`、`max_wait`、`explicit`、`long_input`、`manual`
- `model_config_id`
- `model_provider_snapshot`
- `model_base_url_snapshot`
- `model_name_snapshot`
- `model_config_hash`
- `profile_generation`
- `status`：`pending`、`budget_wait`、`model_started`、`completed`、`retry_wait`、`blocked_config_changed`、`dead`、`cancelled`；过期恢复兼容 `leased`，当前新任务不写入该状态
- `observation_count`
- `input_character_count`
- `estimated_input_tokens`
- `attempt_count`
- `available_at`
- `lease_owner`
- `lease_expires_at`
- `lease_epoch`
- `last_error`
- `created_at`
- `completed_at`

批次创建先读取设置、模型、generation 和按 observation revision 排序的 ready 观察，再通过 `SAVEPOINT` 原子写入固定成员并把观察改为 `batched`；写入时重新核查 generation 和观察状态。当前不是 `BEGIN IMMEDIATE`，也不把前置读取全部包在事务内。普通成员受 12000 去重候选字符和 12 条上限约束，long 单条独立；显式和人工触发优先选择对应候选。候选 hash 相同的成员只发送最新一份文本。批次成员使用独立的 `profile_batch_observations(batch_id, observation_id, batch_index)` 表保存稳定序号和来源关系。

`candidate_kind = 'explicit'` 的 ready 观察可以在前台聊天期间创建 `trigger_kind = 'explicit'` 的高优先级批次；只有领取和模型启动受前台租约限制。它可以与已经 ready 的普通候选合并，但必须服从 12000 字符上限、模型目的地确认和滚动调用预算。

领取通过 `SAVEPOINT` 内的条件更新直接改为 `model_started`，每次领取递增 `lease_epoch`。默认租期 90 秒，模型调用期间每 30 秒续租；续租只允许 `model_started`，续租失败的 worker 返回错误。完成事务必须同时满足 generation、`status = 'model_started'`、owner 和 epoch 匹配并且没有提交账本；当前提交条件不单独检查 `lease_expires_at`，旧 owner/epoch 在任务被接管后失效。

### 9.4 `profile_usage_attempts`

- `id`
- `batch_id`
- `started_at_utc`
- `candidate_character_count`
- `estimated_input_tokens`
- `actual_input_tokens`
- `actual_output_tokens`
- `updated_at`

统一领取事务查询最近 60 分钟和 24 小时尝试记录，并通过插入新 attempt 预占调用次数与冻结候选字符预算。如果预算不足，可领取批次直接改为 `budget_wait`，清空租约，并把 `available_at` 设置为预算预计释放时间；不会先标记 `model_started`。预算允许时先标记 `model_started` 并保留 attempt，再重建请求；后续取消、构建失败或模型失败均不退还预占。实际 usage 仅在 provider 返回时补记。估算输入 Token 当前为候选字符数加 500，只用于展示，不作为账单依据。

### 9.5 `user_profile_facts`

- `id`
- `dimension`
- `normalized_value`
- `display_value`
- `category`
- `global`
- `confidence`
- `extractor_model_config_id`
- `last_observation_revision`：拒绝较旧来源覆盖较新事实
- `created_at`
- `updated_at`

### 9.6 `user_profile_fact_sources`

- `fact_id`
- `observation_id`
- `source_message_id`
- `created_at`

一个事实可以关联多个来源。提交时只接受仍存在的源消息；如果某个操作引用的来源已经全部删除，则丢弃该操作。已经形成事实的来源行在消息或观察被删除后保留，其引用通过 `ON DELETE SET NULL` 置空，事实本身不自动删除。

### 9.7 删除屏障与提交账本

新增：

- `profile_state(profile_generation, next_event_revision, skipped_observation_count, updated_at)`：为观察和删除分配数据库内单调 revision，并累计本地过滤次数；清空画像或关闭功能时递增 generation，旧 generation 批次不得提交。
- `profile_fact_tombstones(dimension, normalized_value, delete_revision, deleted_at)`：单条删除画像时记录删除水位，时间戳只用于展示。
- `profile_batch_commits(batch_id, lease_epoch, applied_at)`：保证同一个批次最多提交一次。
- `profile_foreground_leases(owner, expires_at)`：跨进程记录正在进行的聊天请求。

保存观察和删除画像都会在数据库事务中递增 `next_event_revision` 并取得唯一 revision。单条删除事实和更新 tombstone 在同一事务完成，多次删除保留最新 `delete_revision`。一个断言只有在至少一个仍存在的引用来源满足 `observation_revision > delete_revision` 时才允许写入；同时引用删除前后来源时只保留删除后的有效来源。这样未来新消息可以重新生成事实，而墙上时间回拨和时间戳精度不会影响正确性。

清空全部画像时在同一事务中删除事实、tombstone 和所有观察（包括 processed），递增 generation，并把所有非 completed/cancelled 批次（包括 dead 和 blocked）转为不含来源和模型目的地的 `cancelled` 汇总记录。关闭功能则保留 processed 观察和已有事实。删除观察会级联删除对应 batch-member 关系。批次创建只选择当前 generation 的 ready 观察，新批次继承成员 generation；旧 worker 的结果因 generation 校验失败而不能提交。

## 10. 状态机与重试

```text
observation.pending_preprocess
  -> observation.preprocessing
       |- observation.ready_normal
       |- observation.ready_long
       `- observation.skipped
observation.ready_normal / observation.ready_long
  -> batch.pending
       |- 目的地变化 -> batch.blocked_config_changed
       |- 预算不足 -> batch.budget_wait -> 再次尝试领取
       `- 预算允许且无前台租约 -> batch.model_started
            |- 成功 -> batch.completed + observation.processed
            `- 失败 -> batch.retry_wait -> 再次尝试领取
                  `- 第 5 次失败 -> batch.dead

关闭功能、清空画像或领取时发现全部来源已删除
  -> batch.cancelled
```

- 当前正常失败路径最多尝试 5 次；租约过期恢复直接回到可领取的 `retry_wait`，不在该恢复分支检查次数上限。
- 失败退避使用固定 1、5、15、60、360 分钟数组，第 5 次失败进入 dead；增加随机抖动仍属规划。
- 配置缺失、模型删除和鉴权失败保留明确错误，不降级到其他模型。
- JSON 无法解析或服务错误不应用该次结果；越界维度、无效来源等逐项忽略，合法操作仍在一个事务中写入。整份响应的严格校验仍待实现。
- `dead` 批次不保存消息副本；人工重试时重新从仍存在的源消息构建输入。源消息不存在则取消批次。
- 达到滚动 60 分钟或 24 小时预算时进入 `budget_wait`，到可用时间后重新参与领取，不经过 `pending`；单纯预算延后不增加尝试次数。
- 设置页展示待处理、本地过滤、24 小时用量和合并异常数量，并提供“重试异常批次”；后端状态接口还返回最近完成时间、错误及 blocked 数量，但界面未单独展示这些摘要。本地过滤待确认区通过既有消息引用展示原始用户输入，不在画像表中复制正文。
- batch commit 事务顺序固定为：校验 generation → 校验 lease epoch 和 `model_started` → 校验尚未提交 → 过滤已删除来源 → 校验 tombstone revision → 应用 Reducer → 写提交账本 → 完成批次。

## 11. 桌面端接入

### 11.1 聊天路径

`useChat` 不再调用 `extractPersonalizationMemoryDraft` 或 `savePersonalizationMemory`。后端 `append_message` 在保存用户消息的同一事务内按设置写入观察引用，随后前端继续现有记忆检索和聊天流；聊天路径不执行画像清洗或模型调用。

显式“记住我……”且内容属于画像维度时进入高优先级观察池，不再创建普通记忆；聊天完成后只要调用预算允许即可独立或与已有候选合并处理。界面提示“已加入画像分析”，不能在异步任务尚未完成时声称画像已经保存。显式要求记住普通知识或任务上下文时仍创建普通手工记忆。

### 11.2 设置页

设置插件现在提供两个独立导航页：

1. “用户画像”由 `SettingsProfileTab.tsx` 承载：开关、模型、阈值、调用预算、最近 24 小时用量、任务状态、立即生成、画像列表、本地过滤待确认、单条删除和全部清空。待确认项可逐条加入画像或丢弃；关闭开关会取消并清理待处理任务和待确认项，保留但停止使用现有画像。
2. “记忆库”由 `SettingsMemoryTab.tsx` 承载：只保留普通手工记忆的创建、编辑、启用、搜索和删除能力，以及 Embedding 数据流提示。

画像卡片不再显示“来源记忆 ID”，改为显示来源消息数量、最近更新时间和删除操作。画像没有编辑入口。

## 12. CLI 接入

- 持久化 CLI 会话通过与桌面端相同的 `append_message` 数据库事务自动创建观察。
- CLI 等待用户下一次输入期间可以运行后台调度器；发送正常聊天请求时设置前台忙状态，阻止新的画像调用开始。
- CLI 与桌面端使用相同租约协议，避免双开时重复消费。
- CLI 构建 system message 时读取独立画像表，而不是从个性化记忆聚合。
- 临时会话不收集自己的新画像观察；现有启动提示和帮助说明“不保存会话”，没有专门的画像说明。其后台 worker 仍可处理共享数据库中其他会话已收集的观察。

两端默认通过相同的 app data 路径定位配置库和会话库；CLI 的 `--data-dir` 可指定独立目录。schema 创建保持幂等，但数据库打开时的全量 schema 创建与裁剪没有统一短事务包裹；模型引用镜像同步另使用 `BEGIN IMMEDIATE`。设置变更由 worker 周期及领取时重新读取。首版 CLI 负责生成和使用画像，画像删除与配置管理仍由桌面设置页承担。`nano --prompt` 在输出正常回答后还会 await 一个画像 worker 周期，因此进程退出可能等待该次后台提取完成。

## 13. 对话上下文注入

普通手工记忆继续通过现有 FTS、sqlite-vec 和知识图谱混合召回。画像不进入记忆向量索引，而是由独立查询读取：

- 所有 `global = true` 的事实优先，其中包含回答偏好、姓名和角色；同组按更新时间降序。
- 环境、工作方式、技术栈、项目和兴趣等非全局事实随后按更新时间降序。
- 首版最多取前 20 条事实，事实行正文合计最多约 6000 字符；固定说明和换行另计。当前没有独立的“回答偏好优先于姓名或角色”排序。
- system message 明确规定：只在相关时使用画像；当前用户输入与画像冲突时以当前输入为准。

桌面端和 CLI 使用同一个画像上下文格式化函数，避免行为漂移。

## 14. 兼容与迁移

- 创建新表，不改写现有 `memories` 数据。
- 已存在于当前知识库的 `personalization:*` 标签记录保留为普通记忆，继续具有原来的编辑、启用和删除能力，但不再参与 `get_user_profile` 聚合；旧单库 `nanodesk.sqlite3` 的记录不自动导入当前领域库。
- 删除前端自动个性化写入入口和后端 `upsert_personalization_memory` command；调用搜索确认没有其他运行时依赖，因此不保留兼容壳。
- 新画像从功能启用后的新用户消息开始形成。
- 不据此承诺跨分库版本的自动回滚兼容：当前程序不导入旧单库，旧版本能否读取领域库须按具体版本验证；回滚前应备份数据。

## 15. 隐私与安全边界

以下是启用前数据流告知的设计要求，当前设置页仅有批处理与资源消耗概述、配置名称和模型名，尚未完整展示服务地址、费用和两条画像数据流：

- 使用的模型服务名称、base URL 和模型名。
- 画像候选达到阈值后，会把多条本地筛选出的候选片段作为一次额外请求发送给该服务；普通问答不会默认发送第二次。
- 用户在本地过滤待确认区点击“加入画像”时，会把所选输入作为人工候选发送给该服务；点击“丢弃”不会发送。
- 超长输入会经过本地缩减后单独发送一次。
- 不发送当前画像、助手回复、附件、普通记忆、完整聊天历史和本地标识符。
- 画像提取请求不发送当前画像；但已形成的有效画像会作为个性化上下文进入后续正常聊天请求，这两条数据流必须分开说明。
- 云端模型会产生额外调用费用；模型服务实际部署在本机时，画像提取请求才不会把候选发送到远程设备。
- 滚动 60 分钟和 24 小时调用次数、候选字符预算会限制额外消耗，设置页展示估算 Token 和 provider 可用时的实际 Token。
- 本地保存画像事实、来源关系、批次状态和失败摘要；观察池不复制保存候选正文。

观察池不保存消息正文副本；待处理和失败任务通过消息 ID 回读原始对话。模型请求只用批内稳定序号表达来源顺序，不发送时间戳。

防护要求（需与当前已实现边界区分）：

- 将候选文本视为不可信数据，只允许模型返回 JSON，不允许工具调用。
- 日志不得记录候选正文、画像正文、API key 或模型原始响应。
- 删除全部画像只删除画像事实及来源关系，不删除聊天历史或普通记忆；界面必须明确这一边界。
- 删除聊天时，观察随源消息删除；批次提交会忽略已删除来源。已经形成的画像不会自动删除，用户可在画像区单独删除。
- 关闭画像功能会停止收集和注入，物理删除未处理观察与 batch-member 来源关系，并把未完成批次降为无来源的 cancelled 汇总记录；已有画像事实及 processed 来源保留，重新启用只从新消息开始。

当前模型 HTTP 错误信息可能包含服务返回的响应正文，`last_error` 仅删除控制字符并截断为 500 字符，未做通用脱敏。不能把上述“不记录原始响应或敏感正文”的要求视为已经由错误链路完全保证。

## 16. 验收标准

以下是完整设计的验收目标，不表示所有条目已有自动测试或已经通过。第 19 节列出当前源码中可确认的测试覆盖；未覆盖的并发、重试、严格过滤、输出校验和延迟指标仍待验收。

### 16.1 后端单元测试

- 同一消息重复收集只生成一条观察。
- 3000 个候选字符和 12 条候选观察均能独立触发批次。
- 空闲 30 分钟只有在至少 500 个候选字符时触发；最长等待 24 小时可以处理更短的有效候选。
- 普通提问、一次性任务、第三方信息和无第一人称归属的技术名词不会进入模型请求。
- 明确身份、偏好、长期项目、工作方式和撤回表达能够进入候选池。
- 完全相同的候选 hash 在同一个固定批次只发送一次；覆盖整个 pending 窗口的去重仍是规划目标。
- 显式“记住我……”在聊天完成且预算允许时优先处理；记住错误、知识或任务仍走普通手工记忆。
- 未达到任何阈值时不调用模型。
- 观察完成后台预处理前不能进入模型批次；`ready_long` 永远不会进入普通批次。
- 预处理租约过期接管或 generation 变化后，旧 worker 不能把观察恢复为 ready。
- 超长输入不会与普通观察进入同一批次。
- 纯日志、纯代码和纯 JSON 被跳过。
- 日志前的用户自述被保留，日志正文被排除。
- 单值断言替换旧事实，多值断言去重并存。
- 明确撤回只删除匹配事实，模糊撤回不扩大删除。
- 删除画像后重放旧批次不会恢复事实；新观察可以重新创建。
- observation revision 不受系统时间回拨影响；同时引用删除前后来源时只保留删除后来源。
- 两个 worker 竞争时只有一个能获得租约。
- 租约过期后任务可恢复。
- 租约过期后两个 worker 都返回时，只有当前 `lease_epoch` 可以提交。
- `model_started → 删除 → 迟到完成`、`retry_wait → 删除 → 重试` 和 `清空画像 → 旧批次完成` 均不能恢复已删除画像。
- 同一 batch ID 最多写入一次提交账本。
- 删除模型或改变 provider/base URL/model 后，旧批次进入 `blocked_config_changed`，不会向新目的地自动发送。
- 滚动 60 分钟 2 次、滚动 24 小时 8 次和滚动 24 小时 30000 候选字符预算分别生效；桌面端与 CLI 并发不能超额预占。
- 达到预算的任务进入 `budget_wait`，到滚动窗口的最早可用时间恢复且不丢失观察。
- 失败重试同样消耗真实调用尝试预算。
- 预算不足时可领取批次原子转为 `budget_wait` 并清空租约，不会先写入 `model_started`。
- 显式画像观察创建 `trigger_kind = 'explicit'` 批次，同时仍受调用预算约束。
- 关闭画像会删除未处理观察和 batch-member 来源、保留无来源 cancelled 汇总，并阻止在途结果提交；重新开启只收集新消息。
- 模型失败和非法 JSON 不产生部分画像更新。
- 删除已入批的源消息后，引用该消息的候选操作不会提交。
- 现有普通记忆 CRUD、FTS、向量和图谱测试继续通过。

### 16.2 桌面端测试

- 发送普通消息不等待画像提取完成。
- 设置页可以启停画像、选择模型和调整阈值。
- 设置页可以选择已有的低成本模型、调整调用预算并查看最近 24 小时字符数和 Token 用量。
- 设置页可以查看升级后保留的本地过滤输入，并逐条选择加入画像或丢弃；丢弃不删除原聊天消息。
- 画像不可编辑，可单条删除和全部清空。
- 普通手工记忆仍可编辑和删除。
- 待处理、成功、失败状态不会暴露候选正文。
- 数据流提示准确反映所选模型服务。

### 16.3 CLI 测试

- 持久化会话产生观察，临时会话默认不产生观察。
- CLI 和桌面端共享画像。
- CLI 与桌面端并发时不会重复处理同一批次。
- 桌面端或 CLI 持有前台租约时，另一进程的 worker 不能通过模型启动门；租约过期后可以恢复。
- 新画像能在后续 CLI 对话中进入 system message。

### 16.4 延迟验收

- 聊天发送路径不执行画像清洗；观察引用与用户消息在同一 SQLite 事务内写入。
- 画像调用不被 `await` 在正常聊天完成之前。
- 通过可注入的假模型验证：画像模型延迟或失败不会因同步等待而延迟、取消或改变正常聊天结果。
- 模型网络调用期间不持有数据库锁。worker 遇到数据库忙时立即退避仍是规划目标：当前连接未覆盖 rusqlite 的默认 5000ms busy timeout，数据库操作可能等待锁，桌面 worker 等待期间还可能持有应用内数据库 Mutex。
- 分别记录聊天首字延迟、完整回复耗时和画像批处理耗时，不能用画像总耗时替代聊天延迟指标。
- 在真实云端模型和本地模型场景分别测量 p95 首字延迟；共享资源造成的间接竞争作为运行指标报告，不把“未 await”误称为绝对零影响。

## 17. 实施顺序

以下保留原实施计划，不作为所有步骤和验收已经完成的证明。

1. 先写数据库迁移、状态机和 Profile Reducer 单元测试。
2. 实现观察清洗、候选过滤、去重、调用预算、批次领取、模型协议和失败重试。
3. 将桌面端聊天入口从自动个性化记忆切换到观察收集。
4. 接入 CLI 收集、调度和画像注入。
5. 更新设置页、API 和类型。
6. 删除失效的前端正则画像逻辑，保留普通手工记忆路径。
7. 更新 `README.md`、数据存储、架构和运维文档。
8. 运行 Rust 单元测试、`cargo check --bins`、前端构建、格式检查和差异检查。

## 18. 完成定义

只有在以下条件全部满足时，功能才算完成：

- 画像使用独立表，不再从普通记忆动态聚合。
- 桌面端和 CLI 都能收集并消费持久化观察。
- 普通输入每批每次尝试调用一个模型请求，超长输入独立且不拆分请求。
- 自动路径只有本地筛选出的画像候选片段进入模型请求；人工确认路径按第 7 节发送所选输入。完整排除普通问答误入仍需验收。
- 调用次数、候选字符和 Token 用量可观测并受默认预算限制。
- 模型请求不包含当前画像和规定之外的数据。
- 正常聊天不等待画像生成；画像失败不会取消或改变聊天结果，共享资源的间接竞争按延迟指标如实报告。
- 画像不可编辑、可删除；普通手工记忆 CRUD 不回归。
- 并发、重试、幂等、删除后不被旧任务恢复均有自动测试。
- 用户可在设置页看到准确的数据流说明。
- 相关代码、README 和 `docs` 文档同步更新并通过项目验证命令。
