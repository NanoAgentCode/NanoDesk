# 模块化打包设计（阶段拆分与增量复用）

## 1. 目标与范围

- 将 `npm.cmd run package:win` 的单命令串行流程拆为可独立执行、可单独验证的构建阶段。
- 提速第一优先级为增量复用：前端源码未变时跳过 brand:check + tsc + vite build；Rust 依赖 cargo 增量缓存。
- 快速通道产物保持与现状一致：仅 NSIS 安装包 `src-tauri\target\release\bundle\nsis\NanoDesk_<版本>_x64-setup.exe`。
- 不改变应用代码结构（不做 cargo workspace 拆分），不新增 CLI/MSI 等产物目标。

## 2. 现状基线

当前 `package:win` → `scripts/build-installer.ps1` 一次完成：

1. 定位并注入 MSVC x64 环境（vcvars64、PATH 修正、excpt.h shim）。
2. workspace 路径标记校验（仓库移动时清理 target）。
3. `npm.cmd run tauri build -- --bundles nsis`，其中 `beforeBuildCommand` 固定为 `npm.cmd run build`（brand:check + tsc + vite build），**每次打包全量重建前端**。
4. 校验并输出 NSIS 产物路径（按构建开始时固定的版本号）。

问题：无阶段边界、无计时；前端无增量判断；无法只重跑某一阶段。

## 3. 阶段划分

| 阶段 | ID | 内容 | 增量策略 | 独立入口 |
| --- | --- | --- | --- | --- |
| 0 环境 | env | MSVC 环境采集与注入（现有逻辑抽为公共函数） | 每次执行（秒级，不缓存） | 随任一阶段自动执行 |
| 1 前端 | frontend | brand:check + tsc + vite build → `dist/` | 指纹跳过（见 §4） | `npm.cmd run package:frontend` |
| 2+3 应用+打包 | bundle | `tauri build --bundles nsis`，编译与打包一次完成 | 同形调用，稳态零重编译；跳过 beforeBuildCommand（见 §5） | `npm.cmd run package:bundle` |

独立入口（谨慎使用）：

- `package:app`：`tauri build --no-bundle`，仅用于快速验证 Rust 编译。它会改变 TAURI_CONFIG 使下一次 bundle 流程重链接 nano-desk（实测 ~86s），发布前请回到 `package:win` / `package:fast`。

组合入口（行为一致，均增量）：

- `package:win`（保留）：env → frontend（指纹跳过）→ bundle。稳态零重编译；强制重建前端用 `build-all.ps1 -ForceFrontend`。
- `package:fast`：与 `package:win` 行为一致（保留入口名以兼容习惯）。

## 4. 前端指纹跳过

- 指纹输入：`src/`（排除无关文件如 `*.test.*`）、`index.html`、`vite.config.*`、`tsconfig*.json`、`package.json`、`brand.config.json`、`scripts/sync-branding.mjs` 的相对路径 + 内容哈希，合并计算单一 SHA-256。
- 指纹与 `dist/` 最后写入时间一起存于 `.build/frontend-fingerprint.json`。
- 满足以下全部条件则跳过阶段 1：指纹一致、`dist/` 存在且 `dist/index.html` 存在、指纹文件时间早于 `dist` 目录最后修改时间。
- `--force-frontend` 参数强制重建。
- `tauri dev` 与手动 `npm.cmd run build` 行为不变，不消费指纹。

## 5. tauri build 接入

- 阶段 3 执行 `tauri build --bundles nsis` 前，将 `beforeBuildCommand` 置空（通过 `--config` 覆盖文件传入，不修改 `tauri.conf.json` 原文件），由脚本保证 `dist/` 新鲜。
- 阶段 2（`cargo build --release`）先行预热增量缓存，阶段 3 的 cargo 调用退化为快速 no-op 链接校验。
- 兼容路径：`package:win` 不覆盖配置，仍走原 `beforeBuildCommand` 之外的等价新流程（阶段 1 已含 brand:check + tsc + vite build，与原 `npm run build` 等价），保持产物一致性。

## 6. 计时与可观测

- 每阶段输出 `==> [stage/ID] start/end 耗时`；全流程结束输出阶段耗时汇总表。
- 汇总追加写入 `.build/build-timing.json`（保留最近 20 次），字段：时间戳、入口、阶段、耗时 ms、是否跳过、产物路径。用于对比基线与验证提速效果。

## 7. 保留的既有保障

- workspace 路径标记（`.nanodesk-workspace-root`）清理逻辑保留在阶段 0，所有入口共用。
- 产物校验沿用"构建开始时固定版本号"，防止构建期间配置变更导致的校验错位。
- MSVC PATH 修正（Git link.exe 抢占）与 excpt.h shim 逻辑原样迁入阶段 0 公共模块。

## 8. 脚本结构

```
scripts/build/
  common.psm1        # 阶段0：MSVC 环境、workspace 标记、计时函数
  build-frontend.ps1 # 阶段1：指纹判断 + 前端构建
  build-app.ps1      # 阶段2：cargo release 构建
  build-bundle.ps1   # 阶段3：tauri build NSIS + 产物校验
  build-all.ps1      # 组合入口，等价原 package:win
scripts/build-installer.ps1      # 改为薄封装调用 build-all.ps1，保留兼容
scripts/build-installer.test.ps1 # 保留并扩展
```

- `build-installer.ps1` 保留原路径作为入口（`package:win` 不改命令），内部转发，避免破坏文档与习惯。
- 各阶段脚本支持 `-WhatIf` 式 dry-run 输出将执行的动作与跳过原因，便于验证。

## 9. 验证方式

1. 单测：扩展 `build-installer.test.ps1`——
   - 全流程 mock 构建仍通过（版本固定校验回归）。
   - 指纹跳过：连续两次调用阶段 1，第二次应报告 skipped。
   - 指纹失效：touch 源文件后应重建。
   - dry-run 输出包含阶段计划与跳过原因。
2. 实测：`npm.cmd run package:win` 全量构建记录基线；紧接着 `package:fast` 复测，对比 `.build/build-timing.json` 中前端/Rust 阶段耗时，增量路径应显著缩短（前端阶段 skipped，Rust 阶段走增量缓存）。
3. 产物验证：安装包可执行 NSIS 安装、桌面可启动、版本号与 `tauri.conf.json` 一致。
4. 文档验证：`docs/构建配置与运维.md` 更新新入口说明后，`git diff --check` 通过。

## 10. 风险与对策

- `--config` 覆盖 beforeBuildCommand 与 Tauri CLI 版本行为相关：实施时先以最小实验验证；不兼容则退化为在阶段 1 内用指纹脚本包装 `npm run build`（beforeBuildCommand 指向 wrapper，同样实现跳过）。
- 指纹遗漏输入导致陈旧 `dist/`：指纹计算脚本与 `package.json`/配置文件清单集中维护，任何新增构建输入必须同步登记；测试覆盖 fingerprint 输入清单。
- 阶段拆分后脚本入口变多导致状态不一致：所有入口共享 `common.psm1`，计时与标记文件统一写入 `.build/`，`.gitignore` 已忽略。

## 11. 实现备注（落地差异）

- **组合流程中不存在独立的 app 阶段**（阶段 2+3 合并为一次 `tauri build --bundles nsis`）：实测 `--no-bundle`（app）与 `--bundles nsis`（bundle）交替会改变 TAURI_CONFIG、触发 nano-desk build script 重跑，每次多花 ~86s 重链接；合并后调用形状恒定，稳态零重编译。`package:app` 保留为独立入口（快速编译检查），其代价见 §3。
- **前端指纹跳过对所有入口生效**（含 `package:win`）：原 §3"package:win 全量基线"未采纳——用户目标是无改动时不做任何重编译；强制全量重建前端走 `-ForceFrontend`。
- **不要用裸 `cargo build` 预热缓存**：实测本机环境下 `cargo build` 与 `tauri build` 的编译缓存**双向互不复用**（互换后都全量重编 411 个 crate，约 5 分钟/次），只有 tauri 同形调用才能保证复用；NSIS 打包本身仅占约 25 秒。
- **`--config` 覆盖采用 `{"build":{"beforeBuildCommand":""}}`**（§10 首选方案），实测以 `tauri build -- --bundles nsis --config "<绝对路径>"` 生效；测试覆盖了"bundle 阶段不得触发前端构建命令"。
- **修复了 workspace 标记的 BOM 缺陷**（原 `build-installer.ps1` 遗留）：PS5.1 `Set-Content -Encoding UTF8` 写入 BOM，标记读回比较永不相等，导致**每次打包都误清整个 target 目录**（增量缓存从未真正生效过）。现以无 BOM 写入、读回剥离 BOM。
- **所有含中文的 `.ps1/.psm1` 必须保存为带 BOM 的 UTF-8**：Windows PowerShell 5.1 对无 BOM 文件按 ANSI 解析，中文注释会导致乱码乃至语法错误。
- 计时日志按 `runId` 保留最近 20 次运行（§6），每次入口调用生成一个 `runId`。
