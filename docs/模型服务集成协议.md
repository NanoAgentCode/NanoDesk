# NanoDesk 模型服务集成协议（服务提供方）

适用对象：实现模型服务、企业网关或协议适配器的开发人员。本文以 2026-10-09 工作区实现为依据，定义 NanoDesk 实际发送和读取的协议子集，不代表完整的 OpenAI 或 Anthropic API 规范。

使用客户端配置服务，请阅读 [模型服务接入指南](模型服务接入指南.md)。

## 1. 集成范围与交付要求

NanoDesk 是调用方。服务方提供 HTTP 接口，NanoDesk 的 Rust 后端发起请求；本文中的地址不是 NanoDesk 对外提供的服务端接口。Tauri command 属于桌面端内部通信，也不是 HTTP API。

| 能力 | 当前接入方式 | 服务方需要提供 |
| --- | --- | --- |
| LLM 对话 | OpenAI 兼容或 Anthropic 兼容 HTTP API | 模型列表、非流式对话、SSE 流式对话 |
| Embedding（文本嵌入） | OpenAI 兼容 HTTP API | 模型列表、批量文本转浮点向量 |
| ASR（语音转文字） | OpenAI 兼容 HTTP API | 模型列表、音频文件上传转录 |
| OCR（图片文字识别） | 本机 PaddleOCR CLI | 兼容的本机可执行程序及模型资源；暂无远程 OCR HTTP 配置入口 |

三类 HTTP 能力可以由同一网关提供，也可以分别配置供应商。只需实现承接的能力，但应把这些模型列入模型列表，方便当前设置页发现和选择。

服务方交付信息至少包含：协议类型、API 基础地址、API Key 获取方式、模型 ID 与用途、上下文长度、Embedding 维度、音频格式/大小/时长限制，以及限流规则。模型 ID 必须与请求中的 `model` 完全一致。

## 2. 地址、鉴权与公共约定

### 2.1 地址拼接

以 `https://ai.example.com/v1` 为 OpenAI 兼容基础地址：

| 方法 | 实际地址 | 用途 |
| --- | --- | --- |
| GET | `https://ai.example.com/v1/models` | 发现模型 |
| POST | `https://ai.example.com/v1/chat/completions` | 普通与流式对话 |
| POST | `https://ai.example.com/v1/embeddings` | 批量文本嵌入 |
| POST | `https://ai.example.com/v1/audio/transcriptions` | 音频转录 |

客户端不会为 OpenAI 兼容服务自动补 `/v1`，也不会剥离已填写的 `/chat/completions` 或 `/embeddings`。如果服务实际使用 `/api` 等前缀，应填写对应前缀。统一供应商地址应填写基础地址。

Anthropic 类型填写 `https://ai.example.com` 或 `https://ai.example.com/v1`，都会得到 `/v1/messages` 和 `/v1/models?limit=1000`。客户端没有模型列表分页循环，服务应在一次响应中返回需要选择的模型。

### 2.2 鉴权与报文

| 类型 | 请求头 |
| --- | --- |
| OpenAI 兼容模型列表、LLM、Embedding、ASR | 密钥非空时使用 `Authorization: Bearer <API_KEY>` |
| Anthropic 对话 | `x-api-key: <API_KEY>`、`anthropic-version: 2023-06-01` |
| Anthropic 模型列表 | 同上；密钥为空时省略 `x-api-key` |

JSON 请求使用 `Content-Type: application/json`；模型列表请求带 `Accept: application/json`。ASR 使用带 boundary 的 `multipart/form-data`。当前没有任意鉴权头、URL 查询密钥、请求签名或 OAuth 刷新配置，其他鉴权方式需由服务方网关转换。

LLM、Embedding 和模型列表仅在基础地址字符串含 `localhost` 时允许空密钥；`127.0.0.1` 不触发该例外。ASR 自身允许空密钥，但通过设置页发现模型仍需满足模型列表的校验。此处描述的是现有客户端判断规则。

JSON 使用 UTF-8。成功返回 2xx；失败返回非 2xx。不要用 HTTP 200 搭配业务错误外壳代替失败状态，客户端没有通用的 `code/message/data` 解包逻辑。

## 3. 模型发现接口

请求：`GET {base_url}/models`，Anthropic 地址规则见第 2 节。

响应示例：

```json
{
  "data": [
    { "id": "company-chat", "capabilities": ["chat"], "context_window": 32768 },
    { "id": "company-embedding", "capabilities": ["embedding"] },
    { "id": "company-asr", "capabilities": ["speech-to-text"] }
  ]
}
```

| 字段 | 类型 | 要求 |
| --- | --- | --- |
| `data` | array | 必需，至少有一个有效模型 |
| `data[].id` | string | 必需，去空白后非空；客户端按 ID 排序并去重 |
| `data[].capabilities` | string[] | 可选，建议提供，参与用途判断 |
| `data[].type`、`data[].task` | string | 可选，也参与用途判断 |
| `context_window` | 正整数 | 可选，聊天模型上下文窗口，单位 Token |
| `context_length`、`max_context_length` | 正整数 | 可选替代字段；按上述顺序取首个存在值 |

用途识别先判断 ASR，再判断 Embedding/Chat；`embed` 或 `pooling` 表示嵌入，`chat`、`completion` 或 `generate` 表示对话，同时具备则为 `both`。`asr`、`transcrib`、`speech-to-text` 等标记表示 ASR。缺少元数据时会按模型名称启发式判断，否则默认为聊天。

应使用清晰的用途元数据，避免 ASR 或 Embedding 模型出现在错误的选择器里。ASR 名称命中也会优先判为语音模型；前端还会对后端判为聊天的模型按名称二次推断，即使元数据声明 chat，含 embed、asr 等标记的名称仍可能改变选择器类别。模型名称与能力应保持一致。未知用途不会自动形成新的 OCR 配置入口。

## 4. LLM：OpenAI 兼容协议

### 4.1 请求

`POST {base_url}/chat/completions`

```json
{
  "model": "company-chat",
  "messages": [
    { "role": "system", "content": "你是一个中文助手。" },
    { "role": "user", "content": "请回复：接入成功。" }
  ],
  "temperature": 0.4,
  "max_tokens": 256,
  "stream": true
}
```

| 字段 | 类型 | NanoDesk 行为 |
| --- | --- | --- |
| `model` | string | 始终发送所选模型 ID |
| `messages` | array | 始终发送，每项包含字符串 `role`、`content` |
| `temperature` | number | 始终发送；采用本次调用值或模型配置值 |
| `stream` | boolean | 流式调用发送 `true`；非流式调用省略 |
| `max_tokens` | 正整数 | 有值才发送，可能由上下文预算链路设置 |
| `top_p` | number | 有值才发送 |
| `reasoning_effort` | string | 非空才发送；取本次调用值或模型配置值 |

服务需支持实际发送的生成参数。只接受 `max_completion_tokens`、拒绝 `temperature` 等不兼容情况，需要在网关转换；当前客户端没有按具体模型自动改写字段的逻辑。

消息内容是字符串，当前不发送多模态内容数组、原生 `tools/tool_choice` 或原生 `tool_calls`。Agent 使用提示词中的 XML 工具调用约定；若要支持工具，模型应在文本内容中按约定输出，原生函数调用字段不会被当前解析器执行。图片附件通过 OCR 工具处理。

### 4.2 非流式响应

```json
{
  "choices": [
    { "message": { "role": "assistant", "content": "接入成功。" } }
  ],
  "usage": { "prompt_tokens": 20, "completion_tokens": 5 }
}
```

`choices` 必需且应非空；客户端读取第一项。`message.role` 和 `message.content` 必须是字符串，`content: null` 不兼容。`usage` 可省略；若提供则 `prompt_tokens`、`completion_tokens` 均需为整数。其他字段可附带，客户端忽略。

### 4.3 SSE 流式响应

使用 `Content-Type: text/event-stream`，每条 `data:` 行是一份完整 JSON，并使用空行分隔事件：

```text
data: {"choices":[{"delta":{"content":"接入"}}]}

data: {"choices":[{"delta":{"content":"成功。"}}]}

data: [DONE]

```

客户端按行处理 `data:`，不支持把同一个 JSON 拆成多个 SSE `data:` 行；各事件 JSON 应保持单行。网关应及时刷新数据，避免缓冲整段回复。当前客户端逐个网络 chunk 解码，UTF-8 多字节字符跨 chunk 时存在乱码风险；这是客户端兼容限制，需在实际服务联调中验证中文长回复。

可选思考片段放在 `delta.reasoning_content` 或 `delta.reasoning`，值为字符串。正文和思考应分别发事件；同一事件同时包含非空正文和思考时，当前解析器优先显示正文。只发送一个 choice，避免多个候选文本被拼接。

发送 `[DONE]` 后应结束响应连接：当前客户端忽略该标记，直到响应流结束才发送完成事件。`finish_reason` 和流式 `usage` 不参与当前结果解析。无效 JSON 和 HTTP 200 流中的业务错误事件可能被忽略，应尽可能在开始流式输出前用非 2xx 返回错误。

## 5. LLM：Anthropic 兼容协议

`POST /v1/messages`，鉴权见第 2 节。

```json
{
  "model": "company-chat",
  "system": "你是一个中文助手。",
  "messages": [{ "role": "user", "content": "请回复：接入成功。" }],
  "max_tokens": 256,
  "temperature": 0.4,
  "stream": true
}
```

多个 system 消息被合并到顶层 `system`，以两个换行分隔；assistant 保持原角色，其他非 system 角色转成 user。`max_tokens` 始终发送，未提供时使用 4096；`temperature` 始终发送；`top_p` 有值才发送。非流式调用省略 `stream`。当前不发送 `reasoning_effort`、`thinking` 或原生工具参数。

非流式响应：

```json
{
  "content": [{ "type": "text", "text": "接入成功。" }],
  "usage": { "input_tokens": 20, "output_tokens": 5 }
}
```

`content` 数组必需，客户端拼接其中的字符串 `text`；`usage` 可省略，若提供则两个 Token 字段均需为整数。

流式响应兼容 `content_block_delta`：

```text
event: content_block_delta
data: {"type":"content_block_delta","delta":{"type":"text_delta","text":"接入成功。"}}

event: message_stop
data: {"type":"message_stop"}

```

客户端实际根据 `data` 内的 `type` 判断，不依赖 `event:` 名称。可读取 `thinking_delta` 中的 `thinking` 字符串，但这不表示客户端会主动启用服务端 thinking 功能。完成后需关闭响应流，其他事件不会作为正文显示。

## 6. Embedding 协议

`POST {base_url}/embeddings`，使用 Bearer 鉴权。无论配置中的 `embedding_provider` 为何值，当前此调用都走 OpenAI 兼容协议。

请求：

```json
{
  "model": "company-embedding",
  "input": ["第一段文本", "第二段文本"]
}
```

`input` 始终是字符串数组，必须支持批量请求。客户端仅发送 `model`、`input`，不会发送 `dimensions`、`encoding_format`、`task_type` 等参数。需要这些参数的服务应提供默认值或由网关补齐。

响应：

```json
{
  "data": [
    { "index": 0, "embedding": [0.12, -0.34, 0.56] },
    { "index": 1, "embedding": [0.23, -0.45, 0.67] }
  ]
}
```

示例用 3 维说明结构，实际维度由所选模型确定。

- `data` 必需；每项必须包含非负整数 `index` 和数字数组 `embedding`，不能返回 Base64 向量。
- 服务方应保证每个输入恰好对应一个向量，`index` 为完整且不重复的 `0..N-1`。客户端按 index 排序，但此函数不校验缺项或重复项。
- 向量应非空、维度一致、数值有限，并避免全零向量；数据类型需能被解析为 `f32`。
- 索引文本与查询文本应使用相同模型和向量空间。更换模型或维度后需重新建立相关索引，不能混用旧向量。

配置未单独填写 embedding 地址/密钥时，底层函数使用同一配置记录中的聊天地址/密钥；embedding 模型为空时默认 `text-embedding-3-small`。集成时应显式选定嵌入模型，不依赖默认值。

## 7. ASR：语音转文字协议

`POST {base_url}/audio/transcriptions`

| 表单字段 | 类型 | 要求 |
| --- | --- | --- |
| `file` | 二进制文件 | 必需，含文件名及音频 MIME 类型 |
| `model` | string | 必需，所选 ASR 模型 ID |
| `language` | string | 可选，仅非空时发送，转为小写两位代码，如 `zh`、`en` |

这是 multipart 文件上传，不是 JSON Base64 上传。桌面前端内部传输 Base64 后，Rust 会解码为文件二进制再向服务上传。当前不发送 `response_format`、`prompt`、`timestamp_granularities`、说话人参数或流式转录参数。

服务应默认返回 JSON：

```json
{ "text": "这是识别出的文字。" }
```

顶层 `text` 必须是字符串，去首尾空白后非空。`result.text`、纯文本、SRT、任务 ID 或需要轮询的响应不兼容；其他附加字段不使用。

| 边界 | 当前行为 |
| --- | --- |
| 文件大小 | 最大 `25 × 1024 × 1024` 字节（25 MiB）；界面提示写作 25 MB |
| 扩展名 / MIME | wav → audio/wav；mp3/mpeg/mpga → audio/mpeg；m4a/mp4 → audio/mp4；webm → audio/webm |
| 录音格式 | 客户端录音转换为 16 kHz、单声道 PCM WAV；文件上传保留原格式 |
| 超时 | 整次 HTTP 请求超时 120 秒 |
| 处理方式 | 整段转录，无实时字幕、说话人识别或自动长音频切分 |

服务应在时限内直接完成转录，并另行声明更严格的格式、大小及音频时长限制。旧版独立 ASR 配置可接受完整 `/audio/transcriptions` 地址，但共用供应商应使用基础地址，供 `/models` 发现使用。

## 8. OCR：当前本机接入契约

当前没有 `POST /ocr` 等远程 OCR API。已有 HTTP OCR 服务不能仅填写 URL 接入内置 `ocr_image`。需要远程 OCR 时，可另行实现 MCP 工具并通过 MCP 使用，或新增客户端适配；这不属于当前内置 OCR 协议。

内置 Agent 调用：

```xml
<tool_call name="ocr_image">
  <path>.nanodesk/uploads/images/example.png</path>
  <output_format>text</output_format>
</tool_call>
```

`path` 是当前项目或普通会话临时根目录内的相对图片路径；`output_format` 为 `text`（默认）或 `raw`。不接受任意外部路径或远程 URL。支持 png/jpg/jpeg/bmp/webp/tif/tiff；OCR 输入最多 8 MiB，聊天图片附件保存上限为 25 MiB。

后端查找 `paddleocr` 可执行文件，支持 `NANODESK_PADDLEOCR_BIN` 指定完整路径。调用 `paddleocr ocr -i <图片绝对路径>`，使用 CPU、`PP-OCRv6_small_det` / `PP-OCRv6_small_rec`，同时传递方向处理关闭、最长边 960、识别 batch 1、CPU 线程 2、MKL-DNN/HPI/CINN 关闭等参数。

CLI 应能接受当前参数，并在 90 秒内退出：

- 非零退出码视为失败，报告退出码及输出；超时会终止进程。
- 成功时合并 stdout/stderr；`text` 模式从输出中的 `rec_texts` 列表抽取文字并以换行连接。
- `raw` 返回合并输出；未抽取到文字时 `text` 也可能返回原始输出或完成提示。因此“进程成功”不能单独证明识别出了文字。

模型资源由本机 PaddleOCR 环境准备，未打包进 NanoDesk；首次下载也可能占用执行时间。运行依赖与完整参数参见 [图片文字识别工具](图片文字识别工具.md) 及源码。

## 9. 错误、超时和联调验收

推荐失败报文（这是服务方建议格式，客户端不按字段分类错误）：

```json
{ "error": { "code": "invalid_api_key", "message": "鉴权失败" } }
```

| HTTP 状态 | 含义与服务方处理 |
| --- | --- |
| 400 / 422 | 参数、格式或模型不兼容，返回可定位的错误说明 |
| 401 / 403 | 密钥错误或无模型权限 |
| 404 | 路由或模型不存在 |
| 413 | 文件/请求超过服务限制 |
| 429 | 频率、并发或额度限制 |
| 5xx | 服务内部异常或暂时不可用 |

LLM、Embedding、模型列表的 HTTP 错误会携带响应正文；正文不得回显密钥或原始敏感输入。ASR 只展示状态码与客户端固定提示，不展示服务错误正文。上述 HTTP 适配函数没有自动重试或 `Retry-After` 处理；上层恢复和模型路由不等于协议层重试。

LLM、Embedding、模型列表使用 `reqwest::Client::new()`，没有显式设置业务请求超时；不要套用 ASR 的 120 秒限制。网关需提供自身超时、连接结束和限流策略。

服务方与使用方联合验收：

| 用例 | 通过标准 |
| --- | --- |
| 模型发现 | 三种用途出现在对应选择器，ID 与请求一致 |
| 非流式 LLM | 字符串回复解析成功；连接测试可通过 |
| 流式 LLM | 中文正文逐步显示，响应流正常结束；需要思考显示时单独验证 |
| 多轮 / Agent | 可处理 system 与历史消息；XML 工具调用经 NanoDesk 工具链执行并继续回复 |
| 批量 Embedding | 两段输入恰好返回两个向量；打乱响应顺序后 index 仍能对应；真实索引及查询成功 |
| ASR | 一段 WAV 和实际使用的文件格式返回非空 text；语言为空与指定语言均符合约定 |
| 失败与限制 | 错误密钥、未知模型、限流、超限和无效响应均不会被误认为成功 |
| 本机 OCR | 测试图片识别出预期文字，raw 能用于排查；超限及失败信息明确 |

## 10. 实现依据

- [llm.rs](../src-tauri/src/llm.rs)：地址、鉴权、模型发现、LLM/SSE、Embedding。
- [models.rs](../src-tauri/src/models.rs)：消息与配置数据结构。
- [asr.rs](../src-tauri/src/asr.rs)：供应商解析、multipart、音频限制和响应处理。
- [lib.rs](../src-tauri/src/lib.rs)：连接测试、PaddleOCR 调用及输出抽取。
- [SupplierModelSelectors.tsx](../src/components/settings/SupplierModelSelectors.tsx)：用途过滤及选择器行为。

本文经过源码核对与示例结构检查；服务方验收仍需对实际部署服务执行，不将静态核对视为生产联调通过。
