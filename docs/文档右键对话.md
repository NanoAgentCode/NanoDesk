# 文档右键对话

## 使用方式

1. 在 NanoDesk 的「系统设置 → 通用设置」开启「文档右键对话」。该设置注册当前用户的菜单，无需管理员权限；关闭开关会移除菜单。应用移动位置后重新开启一次以更新路径。
2. 在桌面或文件夹中右键一个文档，选择「使用 NanoDesk 对话」。Windows 11 的经典菜单入口通常位于「显示更多选项」。无需先启动 NanoDesk；应用已运行时通过单实例转交文件。
3. 文档读取成功后，在悬浮窗输入问题并发送。首次发送时创建普通会话，以文件名命名，显示在主窗口会话列表；短文档直接准备全文上下文，长文档显示分块向量化进度。仅打开或读取失败不会创建会话。索引失败时保留问题和当前会话，可配置嵌入模型后点击「重试文档准备」。
4. 在同一个悬浮窗连续追问，或点击「在主窗口继续」打开同一会话并最小化悬浮窗。关闭悬浮窗保留已发送的消息和文档全文；后台任务继续执行。点击回复下方的「打断」会取消当前后台任务并保留已经生成的内容。

每次右键启动一个新的独立窗口，首次发送创建独立会话，包括再次打开同一个文件。主窗口和悬浮窗使用同一持久化数据和后台执行器；请等待同一会话当前回复完成后再发送下一条消息。未发送的草稿不会保存。

## 文档范围

| 格式 | 读取内容 |
| --- | --- |
| TXT、MD、Markdown、CSV | 全文，支持 UTF-8、带 BOM 的 UTF-16 与 GBK |
| DOCX | 文档正文中的段落及表格文字 |
| PDF | 所有页面可提取的文字 |
| RTF | 可识别的正文、Unicode 转义及格式分隔 |
| XLSX | 全部工作表的单元格内容，输出 Markdown 表格 |
| PPTX | 按页码排列的全部幻灯片文字 |

单文件上限 10MB。首期不支持多选、扫描 PDF 的自动 OCR、加密文档、旧版 DOC、图片理解以及 Word/WPS/阅读器内部的右键菜单。无法读取或无法识别的编码会显示错误并允许重试，不把控制码作为正文发送。

读取的是磁盘上的最后保存版本，首次发送时将文档文本快照持久化到当前会话的文档存储；后续修改源文件不会替换已保存的上下文。第一条消息保存文件引用和用户问题，避免把长文全文塞进聊天历史。旧版本已经保存的全文消息仍可折叠查看。文档原文不进入用户画像采集。

## 长文档处理

右键入口和聊天附件上传共用 `index_rag_file`，单文件最多 200 万字符：

- **短文档**：根据聊天模型可用输入预算动态判断，最多约 4000 个估算 Token；以 `fulltext` 状态保存全文，不调用 Embedding。后台按本轮实际剩余预算读取，多个短文档合计超出预算时也会分组分析。
- **长文档**：约 1600 字符一块，优先在句子或段落边界切分，块间重叠约 180 字符；覆盖全文，不再只保留前 120 块。使用「系统设置 → 模型路由」配置的全局嵌入模型，每批最多 16 块。缺少配置、返回无效向量或某批失败时明确报错，不写入半成品索引。
- **具体问题**：检索最多六个相关片段，结合当前会话历史回答，资料带文件名和分块号。短文档直接加入全文上下文；片段合计超预算时先按问题压缩。嵌入模型改变或向量维度不匹配时提示重新索引，不静默忽略失败。
- **全文总结、关键结论、所有待办等问题**：遍历会话全部文档的全部分块，分组提取与问题相关的事实和来源；每组输入随模型上下文调整，最多约 12000 个估算 Token，大组同步增加摘要输出预算（最多 3000 Token，仍受模型上限限制）。独立分组最多三组并发，按原文顺序汇总，相同输入与输出额度的重复分组只分析一次；请求前串行预留预算，每个结果单独结算。某组失败或预算不足时，等待同批已发出的请求完成并保存成功结果，恢复时只重试未完成部分。中间结果过长时逐级归并，再交给聊天模型汇总。指定章节的问题优先检索对应片段。
- **会话复用**：相同会话内文件名、内容及处理模式一致时复用已有文档；向量模式还核对嵌入服务和模型。主窗口续聊和重新上传同一文件均复用索引。不同会话互不共享检索范围。
- **预算与恢复**：逐块分析计入现有任务步数、费用和时间预算，遵守规划审批、暂停及停止。已完成的分组结果随运行记录保存，同一任务恢复时复用。若模型明确报告分块摘要因输出上限截断，普通文本摘要先自动拆小当前批次（最多四层，子片段保留来源标记）；仅有思考而没有正文的截断，以及 GLM 5.3 系列的强制思考摘要，先增加输出额度，避免重复拆分后重新思考。普通摘要最多 4096 Token，GLM 5.3 摘要最多 8192 Token，仍受模型输出上限、剩余上下文和任务预算限制。截断结果不会作为完整摘要使用；已完成的子片段与截断重试决策随任务保存，预算调整后继续时可复用。达到恢复上限仍被截断时才提示调整模型或按章节提问。模型生成的总结仍可能遗漏细节，关键事实可结合原文核对。

短文档的 `fulltext` 和长文档的 `ready` 状态都绑定会话保存，聊天输入区分别显示「全文」或分块数。索引写入采用事务，替换失败会同时回滚文件、文本块、向量与全文搜索记录。

### 文档级分层概要与进度

#### 文档混合检索

具体问题使用「向量相似度 + BM25 关键词」双路召回，各取最多 20 个候选，以 RRF（常数 60）融合排名，按分块 ID 去重，默认返回 6 块，最多 20 块。两路都命中的片段累加排名贡献；融合分数相同时优先关键词排名，再按分块 ID 稳定排序。返回的 `score` 是融合排名分数，不是余弦相似度或置信概率。

关键词同时匹配文件名与原文，中文使用单字和相邻双字，英文忽略大小写，编号保留完整形式及连字符、下划线、点号分段。BM25 使用现有分块文本在本地计算，不依赖 FTS5 默认分词对中文整句的切分，不新增模型请求，也无需重建已有向量。当前轻量实现会读取本会话分块计算关键词统计，超大文档的本地检索开销仍随分块量增长。

混合检索只覆盖当前会话的长文档索引，短文档继续直接提供全文。嵌入模型变更、向量维度错误或嵌入服务失败仍明确报错，不以关键词结果静默掩盖。全文概要及完整清单沿用下述预处理与全文覆盖路径，不用少量检索片段冒充全文。

#### 导入后的后台预处理

长文档向量索引完成后立即返回，后台使用导入时选定的聊天模型预处理，不阻塞继续输入。短文档仍直接使用全文，不额外调用预处理模型。一次分组请求同时生成章节概要和结构化待办、风险、决策，避免对三类事项分别扫描全文；分组输入最多约 12000 个估算 Token，按模型上下文收缩，最多三组并发。多个导入文件排队处理，每个完成的分组立即保存并更新进度；同批某组失败时仍等待其他请求完成并保留成功结果。

事项包含类别、描述、原文摘录、文件分块号及原文明确的负责人、期限。程序校验摘录必须逐字存在于对应分块，负责人和期限也须在原文出现；空概要、无效 JSON、无法核验的字段和截断响应均不会成为完整结果。同分块、同字段的完全重复事项去重，不跨分块丢弃同名事项；最终回答结合来源合并重叠内容。模型提取本身仍可能遗漏，不能承诺清单绝对完整。

章节概要超过目标容量时逐级归并，所有叶节点和归并节点成功后才发布完整清单及根概要。节点、完成清单和进度复用 `document_summary_nodes` 存储，限定同一会话、文档内容版本、模型配置和提示词版本。删除文档后迟到的结果不会写回；重启后打开会话会恢复未完成任务，失败任务不会因轮询自动重复请求，重新上传同一文档可显式重试并复用已完成组。既有未预处理文档可重新上传一次启用后台预处理。

附件显示「预处理排队中 / 预处理 N/M 组 / 概要归并中 / 概要与清单就绪 / 预处理未完成」，预处理失败原因显示在悬停提示中。后台预处理独立持久化计量，使用系统任务预算的时间、步数、费用上限，不占用本轮聊天预算；达到上限后保留完成部分，调高系统任务预算再重新上传可继续，已用额度不会清零。首次全量处理的计算和费用仍然存在。

回答策略：

- 总结全文、关键结论等概要问题优先使用已完成的根概要，并按引用分块和问题词项补充最多三个本地原文片段，不额外等待一次嵌入或预摘要请求；补充片段明确标记为局部核对资料。
- 待办、风险、决策类全文问题从全部叶节点汇集对应类别，保留逐项原文出处。结构化清单不经过通用概要压缩，超过上下文预算时回退原有完整分析流程，不静默截断。
- 指定章节和具体事实问题仍走原文 RAG；明确说「重新核查、核对、逐段、逐字」等时绕过预处理结果。某份文档未完成、模型或内容版本不同，则不把已有半成品当成会话全部文档的完整资料，保留原有原文/全文分组处理路径。

以下按问题即时生成的概要缓存，继续作为预处理未就绪时的回退路径。

“总结全文、核心内容、关键结论”等概要问题先生成与具体问题无关的事实记录，并在结果超出预算时逐级归并。叶节点及归并节点持久化在会话数据库的 `document_summary_nodes` 中；相同文档在后续问题、新任务及应用重启后复用已完成节点。首次生成仍需分析全文，最终回答按本轮问题组织；概要可能省略细节。

在启动预摘要之前，全文覆盖类问题先检查实际输入预算：系统提示、问题、已有历史、协议余量和模型输出预留全部算入后，若能容纳文档全文，则直接交给最终模型流式回答，不因固定的 6000 Token 检索片段额度而强制预摘要。只有全文放不下时才生成分层概要。GLM 5.3 系列的摘要请求使用 `low` 思考强度，Anthropic 兼容协议也传递该参数；不关闭模型强制思考，不修改用户保存的模型配置或普通回答的思考强度。摘要策略变化使用新的缓存版本。

缓存限定在同一会话的同一文档，校验文件 ID、内容版本、模型配置及其更新时间、服务地址、模型名称、上下文与输出额度、提示词版本和实际输入。模型或文档变化后重新生成对应节点；删除文档时级联清理。只保存完整且非空的成功结果，失败或截断结果不作为可复用概要。预算暂停或部分失败后保留已经完成的节点，继续时补齐剩余部分。

“全部待办、所有行动项、逐条列举”等需要完整覆盖的问题绕过通用概要，仍按原文逐块核查；具体章节或事实问题继续检索相关原文片段，不把概要当作完整清单。

聊天输入区上方显示「文档概要 / 全文分析 / 摘要归并」的阶段、文件名、归并层级和「已完成 N/M 组 · 复用 K 组」。每个独立分组完成后更新，切换会话或在主窗口继续时从后台任务快照恢复当前进度；开始流式回答、暂停、失败或结束后隐藏当前进度。截断后的内部子片段合并完成才计为一组，重复分组按实际独立分析组计数。

分组尚未完成时还显示当前模型请求次数、输出额度及截断重试状态；「0/1」仅表示尚无完整分组，不能代表没有发起请求。直接全文回答不显示预摘要进度，而由普通流式消息展示思考与正文。

## 实现与验证

- `--document-chat "文件路径"` 为专用启动参数，冷启动与单实例回调共用校验逻辑。
- 菜单使用当前用户 `Software\Classes\SystemFileAssociations\.<扩展名>\shell\NanoDesk.DocumentChat`，不改变默认打开方式；可执行程序和文件参数分别加引号。NSIS 卸载时仅清理仍指向本安装目录的菜单。
- 每个 `document-*` WebView 复用 `ChatPane`、`useChat` 与 Rust 后台任务执行器；不复用主窗口未发送的草稿。
- 测试命令：`npx.cmd vitest run --exclude '.build/**'`、`cargo test --manifest-path src-tauri/Cargo.toml --lib document_chat`。
- 原生验收使用 `scripts/tests/document-chat-fixtures.py` 生成格式样本，再运行 `scripts/tests/document-chat-native.py`。原生脚本要求专用测试标识 `com.nanodesk.document-chat-qa`、本地 Vite 服务及可用 WebView2；模型调用使用本地测试服务，不连接外部供应商。
